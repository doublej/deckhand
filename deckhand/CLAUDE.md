# The app

## What this is

The iOS app target: `App`, `Model`, the recorders and the screens under `Views/`. Anything with
no UIKit in it belongs in `DeckhandKit` instead, where `just test` can reach it.

The target is generated by XcodeGen from `../project.yml` — **there is no checked-in Info.plist
to edit**; change `project.yml` and run `just generate`.

## Mental model

`Model` holds the listing and the selection; the files beside it are one feature each
(`Dictating`, `Controlling`, `Filtering`, `Keeping`, `Markups`, `Reading`, `Snaps`,
`LiveUpdates`). `Views/` is the screens, `Views/Session/` the session page's parts,
`Views/Artifacts/` slips,
`Views/Annotation/` marking up a picture (its own packet — read it before touching that folder),
`Views/Archive/` every clip this phone has recorded, `Views/Talk/` the mark itself.
`Views/Artifacts/AloudCards.swift` is the other way a slip can be drawn — cards with the app's own
talk mark, from a page that declared its questions (`Aloud`); `ArtifactView` is the one place that
chooses between it and the web view. `Views/Projects/` is the picker that starts a new session; its state is `ProjectPicker`, in
`Starting.swift` rather than four more properties on `AppModel`, which sits at its 300-line gate.

## Invariants

- **No clip is ever the only copy in `tmp`.** A clip used to live in the temporary directory
  until its upload succeeded, and the upload ran inside `run`, which swallows a throw — so a
  sleeping Mac, a refused token or a timeout left the file there unreferenced and the words
  nowhere at all. Every clip is now filed by `ClipArchive` *before* it goes on the wire
  (`Keeping.swift`), and every outcome is written back onto its entry. Nothing in the app deletes
  a clip: only the sweep, which drops what actually reached a session after seven days, and
  the person, from the archive screen. A clip cut off *mid*-recording is still lost and always
  will be — AAC writes its index on stop, so an unfinished clip is unplayable bytes anywhere.
  `heldClips` is the join from a review card back to the clips its words came from, and it
  is *replaced* on a fresh clip exactly as `hold` replaces the card.
- **The clock starts where a press becomes a recording, not where a finger lands.** `TalkGesture`
  waits a fixed 200 ms before a press counts as talking at all, and no gesture on this phone can
  report the moment a touch began — so `Recorder.spans.arming` measures everything after the
  settle (permission and `AVAudioSession.setActive` are both in it, and both are real) and the
  settle itself is named in the doc comment rather than guessed at. The one span that cannot be
  closed where it is opened is the last: `AppModel.answeredAt` is set when the Mac answers and
  `SessionFoot`'s `.onAppear` closes it, because "the card is on screen" is a fact only a view
  has. It is answered once per clip — the card comes back every time somebody swipes between
  panes, and only the first of those is the one the person waited for.
- **A clip's breakdown is shown twice, drawn once, never in a sheet and no longer in the card.**
  `TimingsView` is the drawing; the clip archive expands a row into it, and the review card's
  round-trip line (`ClipCost`) pulls it down onto a slab of its own beneath the card. It has now
  been in three places and each move was a different failure: a sheet took the card off the screen
  in order to explain the card, and drawing the table *inside* the card doubled the height of the
  thing you were about to send. The slab is on the page, not in the box. Exact milliseconds,
  because a bar with no number cannot answer "which stage and by how much" — the bars behind the
  rows are only there so the answer can be found without reading fourteen numbers first. That line
  is still the one thing allowed to sit below Send: it is a receipt, not a fourth verb, and nothing
  both pressable and consequential goes under the button that sends.
- **The review card's buttons are not in the card, and that is the corner audit's real answer.**
  A 44pt control is a 22pt corner; nested 16pt inside a card whose own corner was 12, the inner
  curve is *wider* than the one containing it, which reads as fighting. Tightening the button to
  `Radius.small` fixed the arithmetic and left a row of small hard rectangles at the foot of a soft
  card. So the nesting went instead: Discard, Edit and Send sit below the container, on the page's
  own ground, nested in nothing — free to be the capsule iOS makes a 44pt control, and the card
  went up to `Radius.extraLarge` because nothing is concentric with it any more. The box now holds
  the prompt and the things that add to it; everything you do *with* a finished prompt is under it.
  A deck column is the exception and keeps all of it inside: 240 points has no room for a row of
  capsules standing on their own.
- **`Rewrites` is the before the card never had, drawn as a diff over the after.** The note said
  *what* the chain swapped; it could not show the sentence those words replaced, so a swap that
  was wrong read as a mishearing and a mishearing read as a swap. It was a whole before-block,
  which asked somebody to read two paragraphs and spot the difference — it is now one paragraph
  with the gone words struck through and the new ones in the card's own ink, off `diffWords`
  (`DeckhandKit/Clips/TextDiff.swift`, where `just test` can prove the ordering). The far end is
  the *prepared* words, never the card's draft: `Filtered` was built about those, so an edit typed
  by hand would otherwise be attributed to a filter that never saw it. utt's own cleanup and this
  Mac's filter chain are two rows rather than one, because the answer to each is in a different
  app. utt's half is nil on every Mac today and draws nothing — the gate is
  `UploadReceipt.uttRewrote`, which asks utt's `stages`
  and never `raw != text`, exactly as utt's own `ProcessedTranscript.changed` does.
- **There is no longer hold to give a second gesture.** A hold of any length already *is* the
  recording, from `TalkGesture.settle` onwards, so the other three things get the press each mode
  does not use: a tap where talking is a hold, a long press where talking is a tap. One
  physical press reaches both, because a release arrives as a tap a moment later — so everything
  goes through `TalkControl.claimed()`, which lets the first gesture claim the touch for
  `sameTouch`. Only `SessionFoot` passes `onReach`: a sessions row spends its tap on opening the
  session and its swipe on starting it, and a deck column spends its own, so neither is handed a
  third meaning on the same touch. That press opens a `confirmationDialog` — Photos, Clipboard,
  Clips, in that order, so the one that was here before is the one nearest the thumb — and it must
  stay a dialog: a `.contextMenu` installs a long press of its own and would take the touch from
  the tap under it, which is this same bug for the third time. Nothing says any of it at rest.
- **A gesture on a list row has to share the touch.** The sessions row has three jobs on one
  touch: tap to open, press to talk, swipe to star. `highPriorityGesture` and `ExclusiveGesture`
  both take the touch and broke the tap *and* the swipe; a `Button` takes it the other way and the
  press never fires; a `DragGesture` sequenced after the long press is read as the start of a
  swipe. What works is the plainest thing: not a `Button`, `.onLongPressGesture` for the press
  (with `onPressingChanged` for hold-to-talk's release, which is why there is no drag in it) and
  `.onTapGesture` for the tap, whose meaning `TalkControl.tapped` decides. `UITests` holds all
  three down, including that a press must not open the session.
- **A `NavigationLink` inside a `List` costs two things**: it draws the system's disclosure chevron
  outside the row's own fill, and it swallows `swipeActions` so a swipe never reveals them. The
  sessions list uses a plain `Button` and `navigationDestination(item:)` instead. The UI test
  caught the second one ("no star action on the row"); nothing catches the first.
- **Hiding the navigation bar takes swipe-back with it.** `SessionView` catches its own, and where
  the gesture lives is the load-bearing part. It is a clear 20pt strip **overlaid on the panes**
  (`SessionView.back`), not a `simultaneousGesture` on the page: the panes are a `TabView(.page)`,
  whose paging is a UIKit pan inside the view, so a simultaneous gesture is recognised *beside* it
  and one drag would page and pop at once. An overlay takes the touch before that pan sees it.
  The edge is the **leading** one — `layoutDirection`, not `startLocation.x < 28`, which was the
  wrong side of the screen in a right-to-left reading. The price is that the leading 20pt of a
  pane no longer scroll vertically; the panes are padded wider than that.
- **Ten talk marks on one screen need `isMine`, not ten recorders.** `AloudCards` draws a mark per
  question against the *one* recorder handed down to it, and `TalkControl(isMine:)` is what keeps
  the other nine at rest — the same arrangement the deck uses for its columns. The accent is
  per-card for the same reason: the card being talked into goes utt orange and the rest stay teal,
  which is the only way a screen full of marks says which one is listening.
- **A turn is drawn as the document it is, through `Markdown` rather than `Prose`.** The two
  renderers differ by what their contract is for: `Prose` shows anything outside its four blocks
  as the characters the model typed, because a summary is written against a prompt this repo owns
  and a briefing that broke that contract must look broken. A turn has no contract to break — it
  is whatever a person dictated or another session wrote, and what another session writes is
  markdown. `Prose` is not to be widened to cover it, and a third renderer would be a third place
  the fence rule could drift out of step.
- **A mermaid fence draws, and the seam is the environment.** `Markdown` (in DeckhandKit) knows a
  diagram when it parses one; drawing it needs a web view, which cannot live in that module. So
  the app hands the renderer in at the root with `.diagrams { }` and `Views/Diagrams/MermaidBlock`
  does the work. mermaid is **bundled** (`deckhand/Resources/mermaid.min.js`, MIT, 11.12.3) and
  injected as a `WKUserScript` — host-initiated, the lane the slip bridge already uses — so a
  diagram draws with the Mac asleep and no policy was loosened. A web view has no opinion about
  its own height, so the page measures what mermaid drew and posts it back; a diagram that will
  not parse posts zero and the block falls back to the source lines, which is what every surface
  did before any of this existed. Slips do **not** get this yet: an artifact page is sandboxed by
  its own CSP and nothing injects mermaid into one.
- **The orders pane writes on a sheet, and it has to.** `OrdersView` shows what a session has been
  told to keep in mind and opens `Editor` to change it. A field on the pane itself would put a
  second `TalkControl` on a screen that already floats one over it: two controls reading the one
  recorder, both live, one filling a box and the other sending to the session — the `isMine`
  arrangement `AloudCards` uses cannot help, because these two do different things with the same
  clip. A sheet covers the mark, so the only control listening is the one under your thumb, and
  `Editor` already opens focused with the keyboard up. Its own loading rather than an `AppModel`
  extension, because `deckhand/` sits on its 16-file gate and nothing outside that pane wants it.
- **The transcript poll asks for what is on screen, not for a fixed page.** It fetched the newest
  eight every five seconds and replaced the list with them, so a step back into the conversation
  was taken away again before it could be read — which is what "I cannot see the whole transcript
  after a restart" actually was: nothing is kept on the phone and nothing needs to be, the Mac has
  the file and does the parsing (`page_turns`, `?before=`). `AppModel.shown` is the poll's limit
  and it grows with `turns.count`. Two things follow. The auto-scroll watches
  `turns.last?.timestamp`, never `turns.count` — reading further back grows the list at the far
  end, and pinning to the bottom on every growth throws you straight out of where you went. And
  the row ids are positions, so a prepend renumbers everything: `TranscriptView.step` scrolls to
  index `added` afterwards, one runloop hop later, or the reader lands wherever the new page
  begins.
- **The panes are swiped between, and there is no bar at the foot.** Four words across every
  screen to choose between four screens was a band of chrome doing what a swipe does for free, so
  `pane` is a `TabView(.page)` and the bar is gone — the panes are that much taller and the talk
  mark sits where the bar was. Its native index display is **off**: those dots land exactly where
  the mark floats. The indicator is a dot per pane on the header's meter row instead, which was
  already being drawn and had the space spare, so the whole change costs nothing and returns a
  band. Two things follow. The dots are not a control — dots you can hit are dots somebody will
  try to hit — and the page's own edge-swipe-to-leave has to be arbitrated against the paging
  rather than restricted to the first pane. It fires from **every** pane, and the strip that
  catches it wins by being drawn over them.
- **The session header is a name and a menu, and everything else is the row under it.** The
  chevron and the glyph tile both went: the panes are swiped between and a swipe from the leading
  edge of any of them leaves the session, so the arrow was a second way to do what the page
  already does, and a session's glyph tells one row from another in a *list* of them — on the
  session's own page there is only one session. The way out is still named in the menu, because
  a gesture nobody is told about is not a way out for somebody using VoiceOver. Under the name
  sits everything that is true of the session rather than something you press: the window as a
  13pt ring (a bar ran the width of the page to say one number, and read as the page's progress
  rather than the session's), the count, BUSY or IDLE, and the pane dots. The relative time is
  drawn **only when idle** — `updated_at` is the age of an idle session and nothing else.
- **A swipe names where it landed, then stops.** Four dots say how many panes there are; they
  cannot say which one this is, and a swipe can be accidental. So the pane's name slides in at
  the top and leaves after a second. It takes no touch and it must never become permanent — a
  label that stayed would be the tab bar again under another name.
- **A control that fires a request has to say so where the thumb is.** The slip's send button
  answered, delivered, and looked dead: the only receipt was in the bar at the top of the screen
  and the button is at the foot of a long scroll. It got pressed again, and every press was
  another answer into the session. So it says "Sending…", it refuses a second tap while one is
  in flight, and success closes the screen — a web slip closes itself with `deckhand.close()`,
  and anything the app draws in place of a page has to do that job itself.
- **A sequenced gesture eats the tap beside it, and it does so silently.** `.gesture(LongPress
  .sequenced(before: DragGesture(minimumDistance: 0)))` with `.onTapGesture` outside it claims the
  touch on the way *down*, so the tap never fires however short it is — no error, no warning, the
  handler simply never runs. That was `TalkGesture`'s `.hold` branch, which is the default mode,
  which means the clip archive was unreachable from a session's page for as long as it was written
  that way, and the three-option menu that replaced it inherited the silence. `.onLongPressGesture`
  + `.onTapGesture` is the pairing that works — a list row has always used it for this exact job.
  Both `.hold` branches are one case now. Two UI tests hold it down, one per mode, and the
  *difference* between them is the diagnostic: the menu worked on a long press in tap-to-talk and
  did nothing on a tap in hold-to-talk, which is what narrowed a screenful of suspects to one line.
  Neither a titled dialog nor giving each presentation its own host changed anything, so four
  presentations on one view is measured and fine rather than merely feared.
- **Two gestures on one control means one modifier, and the order inside it is the bug.** The
  archive gesture went on as a second `ViewModifier` wrapping `TalkGesture`, which put its long
  press *outside* the tap — and a long press applied outside a tap takes the touch, so
  tap-to-talk stopped working entirely while hold-to-talk was fine. Every working pair in this
  file is long press **inner**, tap **outer**; they are in one modifier now so the order cannot
  drift apart again. The release of a long press also arrives as a tap a moment later, and in
  tap-to-talk a tap starts recording — so letting go claims the touch, or reading your clips
  would open the microphone behind them.
- **The mark says nothing at rest, and that includes the archive.** A standing "· HOLD FOR CLIPS"
  was tried as a footnote to the gesture nobody can discover by trying it, and it was on screen
  every second the app was open to explain a thing you do once. It is gone. Nothing is labelled
  at rest here — the rule has no exception, and the exception is what made it noise.
- **The word changes, the pill does not.** `.id(word)` was on `TalkMark.pill`, so every new word
  tore the whole capsule down — fill, shadow and all — and built another. Invisible while a wait
  said one word; once the wait learned to narrate itself (`ClipNarration`) it was the button
  flashing in and out six times. `WordRoll` is the fix and the *layout* rule inside it is the part
  worth keeping: the incoming word is a hidden `Text` that owns the container's size and the pair
  actually animating hangs off it as an overlay, out of layout entirely — so the capsule makes one
  smooth resize from the first frame rather than settling after the letters land, and a staggered
  letter arrives where it will finally sit instead of sliding into place. The mark cannot be
  shoved either way: each wing is a `maxWidth: .infinity` half and the pill grows about its own
  centre inside it. Two styles, switched by `@AppStorage("talk.letters")` and a row in Settings —
  a design question with an answer coming, not a preference worth putting in `Preferences`.
- **The talk control is a mark and nothing else.** It floats over the pane rather than sitting
  under it, and the scrolling panes add `TalkMark.clearance` to the end of their content so
  nothing is stuck behind it. No bar, no ground, no resting label: a band of furniture across the
  page to hold one button was the first thing asked to go. What a tap will do slides out on a pill
  to the left, the way out to the right, and both the mark and that left pill send — the pill
  reads as an instruction otherwise. Because it floats, `TalkControl` sets **no** `contentShape`
  of its own: the hit area is whatever the caller drew, or an invisible full-width slot would
  swallow taps meant for the page behind it. Nothing is labelled at rest, so the UI test looks for
  the mark's `talk-mark` identifier.
- **Reading it first is on by default.** Speaking into a busy session cannot be undone, so the
  transcript is held in a card — utt's own review HUD, minus the keycaps a phone has no use for —
  until it is sent or discarded. Off in Settings sends the moment the words come back. A prompt a
  filter stopped goes back into the review card rather than only into the status line: the card is
  the one place words exist unsent and it is editable, which is the only useful answer to "a filter
  will not pass that".
- **Recording pins the phone's orientation** (`OrientationLock`, and the one reason this app has a
  UIApplicationDelegate). Portrait and landscape are two different screens here, so a rotation
  swaps the view holding the recorder and the clip goes with it.
- **A filter's settings are saved on dismissal, not per change.** A text field changes per
  keystroke — the same thing that produced 40-odd revisions in four seconds on the Mac's own
  plugin page — so `onDisappear` covers both Done and a swipe-down, and a dirty flag means no PUT
  when nothing changed.
- **A raw JSONL line cannot be one unwrapped `Text`.** The first raw-transcript view was a single
  `Text` of the whole file inside a `ScrollView([.horizontal, .vertical])`. Unwrapped, a 10k-char
  line is tens of thousands of points wide, and past that CoreText renders **nothing** — a black
  screen, no error, no warning. It is one wrapped `Text` per line in a `LazyVStack` now, and it
  says how many lines arrived so that empty never looks like broken again.
- **A picture is never pinned to nothing.** `AppModel.attach` opens the review card holding just
  the picture when there is not one already. Every caller but the mark's own menu has a card on
  screen by definition, so the guard is dead code for them; without it a picture put up from the
  mark at rest went into `attached` with nowhere to draw it — not lost, since the next clip
  transcribed opens a card already holding it, but off the screen until then, which from the
  outside is a picture that was dropped. An empty card is the surface for talking about a picture
  and it already exists: `SayRest` is on it, a tap on the thumbnail opens the marking sheet, and
  Discard throws the picture away with the words. `hold("")` is still the one door in, so the
  chain's notes stay nil rather than becoming an empty `Filtered` nothing wrote.
- **A `PhotosPicker` cannot be a `Menu` item.** It is a control, not a button, and a menu row built
  from one opens nothing at all. `.photosPicker(isPresented:)` is the same picker with the trigger
  separated from it, which is what a menu needs — `ReviewCard.pictures`.
- **`PhotosPicker` needs no usage description**, and `UIPasteboard.hasImages` needs no permission —
  which is why the clipboard button only appears when there is something to paste: asking
  `UIPasteboard.general.image` is what triggers the system's paste consent, and only then.
- **A busy session cannot be made to read early.** The queue drains when a turn ends, so the
  phone's "force" is Escape and the button says "Stop the run so it reads this".
- **ATS:** the app talks plain HTTP to a `.local` name, which needs `NSAllowsLocalNetworking` plus
  `NSLocalNetworkUsageDescription` — both in `project.yml`, not a checked-in plist.

## Running it on hardware

- `just sim` builds, installs and launches in the simulator, already paired.
- `just device` (`just phone="Pocketline Swing" device`) takes four things, and the error names
  whichever is missing: Xcode signed in to the account for team KA6433FU8U;
  `-allowProvisioningDeviceRegistration` alongside `-allowProvisioningUpdates`, or a phone not
  already in the team's wildcard profile is refused with "isn't registered in your developer
  account"; an **unlocked** phone, or the developer disk image will not mount; and, the first time
  a phone gets a build from this team, the profile trusted by hand in Settings → General → VPN &
  Device Management. Deployment target is iOS 18.0 — the 12 Pro runs 18.7.
- `xcrun devicectl device process launch ... -- -deckhand.host <host> -deckhand.token <token>`
  starts the app already paired; the model writes launch-argument settings back to defaults, so
  the pairing survives a cold start. The `--` matters: devicectl eats the flags without it.

## Verification

`just build` and `just test`; `just ui-test` drives the simulator against a daemon started with
`just daemon`. The app build needs the simulator named in the Justfile's `sim`.
